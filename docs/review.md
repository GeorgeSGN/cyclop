# Отчёт для ревьюера

Форк [akalikbergenov/cyclop](https://github.com/akalikbergenov/cyclop) (MIT) под личное
использование. Дата: 2026-08-06. Ветка: `main`, upstream — `upstream/main`.

Приложение — панель, живущая в чёлке MacBook: раскрывается по наведению курсора,
складывается когда курсор уходит. Нативный SwiftUI + AppKit, ноль внешних
зависимостей, сборка через SwiftPM без Xcode-проекта.

## Как ревьюить

```bash
git clone git@gitlab.com:george_ns/cyclop.git && cd cyclop
git remote add upstream https://github.com/akalikbergenov/cyclop.git && git fetch upstream

git diff upstream/main..HEAD          # весь дифф от оригинала
git log --oneline upstream/main..HEAD  # актуальный список коммитов

./Scripts/bundle.sh release && open build/Cyclop.app
```

Требуется macOS 15+ и Swift 6. Сборка занимает секунды, тестов в проекте нет —
ни в оригинале, ни здесь.

## 2. Копирование с полки

**Проблема.** Выделенную карточку нельзя было скопировать с клавиатуры: ⌘C на
полке не доходит до приложения вообще. Панель забирает клавиатуру только на
вкладках с текстовым полем, на полке она никогда не key-окно.

**Решение.** Не ⌘C, а копирование в момент выбора: `ShelfStore.select()` в
дополнение к выделению кладёт выборку в буфер.

**Почему не ⌘C.** Чтобы он работал, панель обязана стать key-окном, а это тускнит
заголовок и гасит каретку в окне под панелью — ровно та цена, из-за которой автор
включил клавиатуру только на вкладках с полем. Клик закрывает задачу без неё.

**Что проверено по коду, а не предположено:**

- `ShelfDragSource.mouseUp` вызывает `onClick` только если драга не было —
  перетаскивание карточки буфер не перезаписывает;
- `ClipboardStore.poll()` выходит на маркере `com.cyclop.internal` — копии с
  полки не засоряют историю буфера.

Точное правило — **буфер зеркалит текущую выборку**, а не «снятие ничего не
трогает»: ⌘-клик, убравший одну карточку из трёх, перепишет буфер оставшимися
двумя, потому что выборка на экране, расходящаяся с тем, что вставится, хуже
любого из двух вариантов. Нетронутым буфер остаётся только при полном снятии
выделения — пустая запись забрала бы скопированное и не дала взамен ничего.

Двойной клик (он открывает файл) проходит через тот же обработчик с
`clickCount == 1`, так что открытие карточки по пути её копирует.

## 3. Мультивыбор: пути вместо картинки

Здесь была ошибка в первой версии, поэтому подробно.

Сначала при мультивыборе в каждый элемент буфера кладлась и ссылка на файл, и
сама картинка. Замер показал, что буфер формируется правильно (3 элемента,
`public.file-url` + `public.png` в каждом), но Claude Code в терминале вставлял
одну картинку.

**Причина.** Claude Code читает буфер через
`osascript -e 'the clipboard as «class PNGf»'` — один запрос, одно значение.
Найдя картинку, он до текста не доходит. То есть картинка в буфере **блокирует**
альтернативный путь, а не дополняет его.

**Итог.** Байты картинки кладутся только когда скопирована одна карточка. При
нескольких — ссылки на файлы плюс список путей текстом:

| | одна карточка | несколько |
|---|---|---|
| Finder, мессенджеры | файл ✓ | все файлы ✓ |
| редактор, чат картинкой | картинка ✓ | ничего |
| терминал, читающий путь | картинка ✓ | все файлы ✓ |

Проверено на живом буфере: `PNG нет`, 3 × `file-url`, текст с 3 путями; Claude
Code разобрал список и подтянул все три файла.

Побочно исправлен баг оригинала: JPEG отдавался под типом `.tiff` — байты JPEG с
заголовком «это TIFF», такую картинку не декодирует никто. Теперь PNG идёт как
есть, остальное переупаковывается в настоящий TIFF.

Предохранитель `imageDataBudget = 64 MB` сторожит теперь один случай — одну очень
большую картинку. Мультивыбор байты не читает вообще, так что ⌘-клик по
шестидесяти карточкам до этой проверки уже не доходит.

## 4. Автоудаление скриншотов

`ScreenshotVault.prune()` удаляет снимки старше 14 дней **безвозвратно**, не в
Корзину. Запуск при старте и раз в сутки (`AppDelegate.startSweep`) — дневной
такт нужен маку, который не перезагружается месяцами.

**Расхождение с оригиналом намеренное.** У автора папка не чистится никогда, это
заявленный принцип: «папка принадлежит пользователю». Здесь снимок из буфера
считается одноразовым, а Корзина, медленно заполняющаяся такими, — та же проблема
на папку дальше.

Карточки на полке не исключение: две недели значит две недели, иначе полка
становится тем самым вечным хранилищем. После уборки вызывается `reloadShelf()`,
и карточки с исчезнувшими файлами уходят.

### Что считается «своим»

**Только файлы с расширенным атрибутом `com.cyclop.saved`**, который `save()`
ставит сразу после записи. Имя доказательством авторства быть не может: macOS
называет свои снимки `Screenshot <дата> at <время>.png` — формат совпадает с
нашим почти дословно, — а по-русски её `Снимок экрана …` начинается с того же
слова. Достаточно перенести системную папку скриншотов сюда (папка ведь так и
называется), и уборка по именам удалила бы их безвозвратно.

Три следствия этого решения, каждое намеренное:

- **Снимки, сохранённые до появления метки, не удаляются никогда** — метки на них
  нет. Это безопасная сторона ошибки. Десять файлов, лежавших в папке на момент
  правки, помечены **разово руками** (`xattr -w`): на той машине они доказуемо
  наши — `com.apple.screencapture location` не задан, то есть системные снимки
  идут на Рабочий стол. В коде миграции нет и не будет: «пометить всё, что похоже
  по имени» — та самая догадка, от которой мы ушли, и на машине с перенесённой
  системной папкой она пометила бы чужое.
- **Копия нашего снимка наследует метку.** Finder и Preview сохраняют xattr при
  копировании, так что копия, оставленная в этой же папке, будет подметена как
  наша. Технического ответа тут нет — снять метку не у кого спросить, — так что
  это известная граница: папка не место для правок, которые нужно сохранить.
- **`clear()` и `usage()` намеренно шире.** Пункт меню «Очистить папку снимков»
  работает по всей папке и кладёт в **Корзину**; размер в его заголовке считает
  ровно то, что он удалит, — эти двое согласованы между собой. С `prune` они
  расходятся, и это не недоделка: явное нажатие — решение, поэтому обратимое и
  полное, а расписание никто не звал, поэтому оно узкое и окончательное.
  Сузить `clear()` до помеченных значило бы оставить папку непустой после
  «очистить папку», без всякой возможности увидеть почему: метка невидима.

## 5. Вкладка «Утилиты»: блокировка клавиатуры

Пятая иконка в рейле, внутри — одна кнопка во всю плашку. Не список из одного
элемента: раскладку под то, чего ещё нет, пришлось бы угадывать сейчас и
переделывать потом.

**Механизм.** `CGEventTap` в режиме `.defaultTap` на `.cghidEventTap`, маска
`~CGEventMask(0)` — все типы событий, а не список. Колбэк возвращает `nil`, что
и есть отбрасывание события.

**Требует Accessibility.** Это первое TCC-разрешение приложения, и его не
обойти: единственная альтернатива — перетянуть фокус на своё окно, и тогда ⌘Q,
⌘Tab, Caps Lock и клавиши яркости всё равно проходят. Приложение, которое
выглядит заблокированным, но не заблокировано, хуже отсутствия фичи: тряпке
доверяют под обещание, которое не выполняется.

Разрешение спрашивается не сразу: первое нажатие показывает объяснение в панели и
поднимает системный диалог, второе (если разрешения всё ещё нет) открывает нужный
раздел настроек. Диалог, выпрыгнувший до объяснения, неотличим от программы,
которая сама полезла к вводу.

**Три выхода из режима, независимые друг от друга:**

1. удержание **Esc** или **`-`** (`KeyboardLock.holdToRelease`, сейчас 2 с; все
   тексты берут число оттуда, чтобы не разъезжаться) — клавиши матчатся по key code, а не
   по символу: на кириллице сравнение по символу молча не сработает, автор уже
   поймал это на ⌘C. Автоповтор keyDown отсчёт не сбрасывает, любая другая
   **обычная** клавиша — сбрасывает. Модификаторы приходят как `.flagsChanged` и
   не сбрасывают ничего намеренно: Shift, задетый тряпкой, не должен стоить
   выхода из режима, где больше ничего не работает;
2. **автоснятие через 60 секунд**, неотключаемое;
3. macOS сама выключает tap, если колбэк перестал отвечать (`tapDisabledByTimeout`).
   Обработано с повторным включением — разница между блокировкой, которая
   восстановилась, и той, которая молча перестала блокировать.

Плюс четвёртое, вне кода: tap умирает вместе с процессом, так что kill снимает
блокировку.

Отказы типизированы (`KeyboardLock.Refusal`) и публикуются, а не только
возвращаются: у одной из причин нет вызывающего — secure input, поднявшийся
посреди протирки, снимает блокировку из таймера, и без публикации оверлей просто
исчезал бы, что читается как сбой. Панель показывает причину и что с ней делать.

Причин **два поля с разными временами жизни**, и это не дублирование:

- `refusal` — почему нажатие не смогло начать. Гасится входом на вкладку:
  разрешение могло быть выдано в промежутке;
- `interruption` — почему работавшая блокировка кончилась сама. Переживает
  возврат на вкладку, гасится следующим нажатием и **устаревает через минуту**
  (`interruptionShelfLife`): это сообщение о событии, а провисев долго, оно
  начинает читаться как описание текущего состояния — «сломано сейчас» вместо
  «прервалось минуту назад». Минута взята из этого прочтения, а не из механики:
  технического момента, в который причина перестаёт быть верной, не существует.

Одним полем это не выражается. Содержимое панели живёт под `if isOpen`, а
блокировка панель складывает — то есть в момент, когда причина записывается,
вкладки в иерархии нет, и её `onAppear` при возврате гасил бы ровно то
объяснение, за которым пользователь и пришёл.

Снятие блокировки по истечении удержания идёт через **дренаж**: оверлей уходит
сразу, а tap живёт до `keyUp` клавиши выхода (потолок — 2 с на залипшую клавишу),
гася по пути хвост автоповтора. Иначе отпущенный на секунду позже `-` насыпал бы
дефисов в активный документ. В дренаже гасятся только клавиатурные события, так
что курсор жив с момента, когда вернулся экран.

**Оверлей** (`CleaningOverlay`) — чёрное окно на каждом дисплее, уровень
`CGShieldingWindowLevel()`. Две причины: заблокированный мак, выглядящий обычно,
неотличим от зависшего, а на чёрном фоне видны разводы, так что экран протирается
в том же проходе. Подсказка и прогресс удержания показываются на дисплее под
курсором. Подписка на `didChangeScreenParameters` — подключённый в процессе
монитор иначе остался бы неприкрытым.

Первая версия накрывала внешний монитор частично, прямоугольником не по месту.
Причина — `NSWindow(contentRect:…screen:)` читает rect относительно левого
нижнего угла переданного экрана, а `screen.frame` уже глобальный, так что origin
складывался сам с собой. Замер на двух дисплеях:

```
внешний: screen.frame = (1728, -323, 2560, 1440)
было  → окно в (3456, -646)   ← 1728+1728, -323+-323
стало → окно в (1728, -323)   ← setFrame, координаты глобальные
```

Окна теперь создаются с нулевым rect и позиционируются `setFrame`, которому
перевод координат не нужен.

Панель при блокировке закрывается, поллинг курсора останавливается: пока события
гасятся, отслеживать нечего.

## 6. Панель, застревавшая раскрытой

Найдено в работе, не ревью. Симптомы выглядели как два разных бага:

- панель со вкладкой перевода не закрывалась вообще — уводишь курсор, а она
  висит; помогало только переключение на другую вкладку;
- кнопки в ней переставали нажиматься: клик по крестику уходил в приложение
  **под** панелью.

**Причина одна.** Логическое состояние и картинка расходились: код уже считал
панель закрытой, а на экране она оставалась раскрытой. Отсюда всё: закрывать
нечего — она «закрыта»; курсор ни на что не влияет — реагировать не на что;
клики промахиваются — область приёма мыши сжимается вместе с состоянием, а
нарисованная панель остаётся большой.

**Как поймали.** Временное логирование в пяти точках плюс снимок состояния раз в
две секунды, пока панель открыта. Решающим оказалось отсутствие этих снимков в
момент, когда панель висела на экране: значит `isOpen` уже `false`.

**Механизм.** Ключевой статус отдаётся единственным доступным способом —
`orderOut` + `orderFrontRegardless`, то есть окно на миг выдёргивается и
возвращается. Делалось это прямо из `acceptsKeyboard`, до сворачивания, и
выдёргивание попадало в момент анимации, унося её перерисовку. Автор уже
разводил отдачу клавиатуры и сворачивание по разным проходам цикла из-за
похожего бага — лечение оказалось неполным, потому что порядок остался прежним.

**Правка.** `releaseKey()` вынесен из `acceptsKeyboard` в отдельный метод, и
контроллер зовёт его **после** сворачивания, следующим проходом. Плюс страховка:
после сворачивания перерисовка запрашивается явно — чтобы картинка не могла
отстать от состояния ни при каком порядке событий.

Отдельно выяснилось, что перевод «не работает без пробела» — не баг: он идёт
через паузу в 320 мс после последнего нажатия, и пробел просто чаще всего
оказывается последним нажатием перед паузой.

## 7. Скопированные файлы на полке

`⌘C` по файлам в Finder кладёт их карточками на полку. Отличать файл от текста
не приходится гадая: файл приходит в буфер ссылкой, текст — никогда, и
распознавание уже было в `ClipboardStore` ради истории буфера.

Три решения, каждое намеренное:

- **на полку идут все скопированные файлы**, а в историю буфера — по-прежнему
  одна запись на копию: история отвечает на вопрос «что лежало в буфере», полка —
  «какие файлы под рукой»;
- **переключатель в меню-баре**, отдельный от снимков. Копирование файла — куда
  более проходной жест, чем съёмка экрана: чаще всего это шаг к вставке
  куда-то ещё, и полке ни к чему заполняться этим;
- **вкладка переключается на полку только пока панель сложена.** Снимок стоит
  показать сразу, а выдёргивать видимую вкладку из-под руки посреди перевода
  из-за скопированного файла — грубо.

Полка ссылается на файлы, а не копирует их, поэтому карточка чужого файла
умирает вместе с перемещением оригинала. Попутно исправлено: `load()` теперь
записывает отфильтрованный список обратно — иначе пути пропавших файлов
оставались в настройках навсегда, а с копированием чужих файлов эта куча растёт
заметно быстрее.

## Риски и ограничения

**Подпись и Accessibility — закрыто.** macOS привязывает выданное разрешение к
подписи, а ad-hoc подпись меняется с каждой сборкой, поэтому Универсальный доступ
приходилось выдавать заново после каждой пересборки. Теперь `bundle.sh` подписывает
первой доступной codesigning identity (переопределяется через
`CYCLOP_SIGN_IDENTITY`), и требование выглядит так:

```
identifier "com.cyclop.app" and anchor apple generic
  and certificate leaf[subject.CN] = "Apple Development: …"
```

Хеша кода в нём нет, так что пересборки разрешение не сбрасывают. На машине без
identity остаётся ad-hoc — приложение работает, просто разрешение живёт одну
сборку; текст отказа `.tapFailed` про это и говорит.

**Хвост автоповтора гасится две секунды** (`drainTimeout`). Держать клавишу выхода
дольше — остаток автоповтора уйдёт в активное окно. Проверено на живой машине,
оставлено сознательно: цена — пара символов в текстовом поле, а точное решение
(продлевать дренаж, пока идут автоповторы) не стоит усложнения ради этого.

**Нет тестов.** Их нет и в оригинале. Проверялось запуском и замерами:
структура буфера читалась отдельным скриптом, уборка — на подставном файле со
старой датой.

**Конфликты при обновлении из upstream** ожидаются в `NotchViewModel.swift`,
`NotchContentView.swift`, `ShelfStore.swift`, `ScreenshotVault.swift`,
`AppDelegate.swift`, `Scripts/bundle.sh`.

**Проверено на живой машине** с выданным Accessibility, конфигурация из двух
дисплеев (встроенный + внешний 2560×1440). Замерами:

- геометрия оверлея — до и после фикса координат (см. выше);
- скоуп уборки — подстановкой файлов всех спорных видов: помеченный старый
  удалён, имитация системного снимка (`Снимок экрана …` без метки), чужой `.png`,
  `.txt` и каталог остались;
- метка ставится на новые файлы — положил PNG в буфер, приложение сохранило
  снимок с `com.cyclop.saved`; на файле, созданном до правки, метки нет.

Ручными прогонами под активным перехватом:

| Что | Результат |
|---|---|
| блокировка и выход удержанием | работает |
| `⌘Tab` под блокировкой | не переключает приложения |
| хвост автоповтора (`-` в текстовом поле) | дефисов нет, пока клавиша отпущена в пределах `drainTimeout` |
| повторное нажатие в окне дренажа | нормальная блокировка, выход обычный; мёртвого ввода нет |
| secure input **до** блокировки | отказ «Ввод защищён», экран не чернеет |
| secure input **во время** блокировки | снялась сама; на вкладке дождалось «Блокировка прервалась» |
| отключение и подключение монитора под блокировкой | режим держится, оба дисплея накрыты, нажатия не доходят |

Последние два — проверки замечаний №2 и G, то есть двух самых дорогих правок:
режим отказывается врать, а причина его прекращения доживает до чтения.

**Осталось непроверенным** только то, что недостижимо намеренно или требует
редкого стечения: автоснятие через 60 с (логика та же, что у прерывания),
`.busy` (недостижимо по построению) и `.tapFailed` (системный отказ перехвата).

## На что смотреть в первую очередь

1. `KeyboardLock.handle` — колбэк tap. Гасит всё, работает на главном потоке,
   ошибка здесь означает мак, у которого не работает ввод.
2. `KeyboardLock.unlock` — снятие tap и порядок разрушения. Утечка `CFMachPort`
   или неснятый run loop source оставят блокировку жить.
3. `ShelfStore.copy(_ urls:)` — почему картинка кладётся только для одиночного
   файла; логика неочевидна без контекста из пункта 3.
4. `ScreenshotVault.prune` — необратимое удаление файлов пользователя.
